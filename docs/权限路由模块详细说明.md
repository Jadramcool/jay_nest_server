# 权限路由模块详细说明

## 一、架构总览

本项目的权限路由体系采用 **JWT + RBAC（基于角色的访问控制）** 模型，由以下核心层组成：

```
请求进入
  │
  ▼
┌─────────────────────────────────────────────────┐
│  JwtAuthGuard（全局守卫）                         │
│  ├── 检查 @Public() → 放行                       │
│  └── 无 @Public() → 验证 JWT Token               │
│       ├── Token 有效 → 挂载 user 到 request      │
│       └── Token 无效 → 抛出 401                  │
├─────────────────────────────────────────────────┤
│  RolesGuard（未全局注册）                         │
│  ├── 无 @Roles() → 放行                          │
│  └── 有 @Roles() → 检查 user.roles 是否匹配      │
├─────────────────────────────────────────────────┤
│  PermissionsGuard（未全局注册）                   │
│  ├── 无 @RequirePermissions() → 放行             │
│  └── 有 @RequirePermissions() → 检查 user.permissions │
├─────────────────────────────────────────────────┤
│  Controller Method                               │
│  └── @CurrentUser() 从 request.user 提取用户信息  │
└─────────────────────────────────────────────────┘
```

## 二、核心组件详解

### 2.1 认证层 — JWT 双 Token 机制

| 组件 | 文件 | 职责 |
|------|------|------|
| JwtStrategy | `src/modules/auth/strategies/jwt.strategy.ts` | 从 `Authorization: Bearer xxx` 提取并验证 accessToken |
| JwtRefreshStrategy | `src/modules/auth/strategies/jwt-refresh.strategy.ts` | 从请求体 `refreshToken` 字段提取并验证刷新令牌 |
| AuthService | `src/modules/auth/auth.service.ts` | 登录验证、Token 生成/刷新、用户信息获取 |

**Token 结构**：

- **accessToken** 载荷：`{ id, username }`，有效期默认 7200 秒（2小时）
- **refreshToken** 载荷：`{ id, username, type: 'refresh' }`，有效期默认 604800 秒（7天）

**关键设计**：`JwtStrategy.validate()` 返回 `{ userId, username }`，这个对象会被 Passport 挂载到 `request.user` 上，后续 `@CurrentUser()` 装饰器从这里提取数据。

### 2.2 守卫层 — 三级权限控制

#### (1) JwtAuthGuard — 认证守卫（全局生效）

文件：`src/common/guards/jwt-auth.guard.ts`

```typescript
// 在 auth.module.ts 中通过 APP_GUARD 全局注册
{ provide: APP_GUARD, useClass: JwtAuthGuard }
```

**执行逻辑**：
1. 通过 `Reflector` 检查当前路由方法或控制器类是否标注了 `@Public()`
2. 如果是公开接口 → 直接放行
3. 如果不是公开接口 → 调用 `AuthGuard('jwt')` 执行 JWT 验证
4. 验证失败 → 抛出 `UnauthorizedException('认证失败')`

**影响范围**：全局所有路由默认需要认证，除非显式标注 `@Public()`。

#### (2) RolesGuard — 角色守卫（按需使用）

文件：`src/common/guards/roles.guard.ts`

**执行逻辑**：
1. 通过 `Reflector` 获取 `@Roles()` 元数据
2. 无 `@Roles()` → 放行
3. 有 `@Roles()` → 从 `request.user.roles` 中查找匹配的角色 code
4. 使用 `some` 语义：只要用户拥有任一所需角色即放行

**当前状态**：**未被全局注册**，也未在任何控制器中实际使用 `@Roles()` 装饰器。

#### (3) PermissionsGuard — 权限守卫（按需使用）

文件：`src/common/guards/permissions.guard.ts`

**执行逻辑**：
1. 通过 `Reflector` 获取 `@RequirePermissions()` 元数据
2. 无 `@RequirePermissions()` → 放行
3. 有 `@RequirePermissions()` → 从 `request.user.permissions` 中查找匹配的权限字符串
4. 使用 `some` 语义：只要用户拥有任一所需权限即放行

**当前状态**：**未被全局注册**，也未在任何控制器中实际使用 `@RequirePermissions()` 装饰器。

### 2.3 装饰器层 — 权限元数据声明

| 装饰器 | 文件 | 作用 |
|--------|------|------|
| `@Public()` | `src/common/decorators/public.decorator.ts` | 标记接口无需认证 |
| `@Roles(...roles: string[])` | `src/common/decorators/roles.decorator.ts` | 声明所需角色 |
| `@RequirePermissions(...permissions: string[])` | `src/common/decorators/permissions.decorator.ts` | 声明所需权限 |
| `@CurrentUser()` | `src/common/decorators/current-user.decorator.ts` | 从 request.user 提取当前用户信息 |
| `@OperationLog(options?)` | `src/common/decorators/operation-log.decorator.ts` | 声明操作日志配置 |

### 2.4 数据模型层 — RBAC 关系

```
User ──(多对多)── UserRole ──(多对多)── Role ──(多对多)── RoleMenu ──(多对多)── Menu
  │                                                  │
  └── departmentId ── Department                     └── code (菜单编码/权限码)
```

**核心表**：

| 表 | 用途 |
|------|------|
| `User` | 用户表，含 `roleType` 字段（字符串类型，非外键） |
| `Role` | 角色表，含 `code`（角色编码）和 `name`（角色名称） |
| `UserRole` | 用户-角色关联表 |
| `Menu` | 菜单表，含 `code`（菜单编码）、`method`（HTTP方法）、`needLogin` |
| `RoleMenu` | 角色-菜单关联表 |
| `RoleDepartment` | 角色-部门关联表，含 `autoAssign`（自动分配）和 `defaultPosition` |

### 2.5 菜单权限获取流程

`AuthService.getUserMenusFlat()` 的执行路径：

```
1. 根据 userId 查询 UserRole → 获取用户所有角色
2. 对每个角色查询 RoleMenu → 获取角色关联的所有菜单
3. 过滤：仅保留 enable=true 且 show=true 的菜单
4. 去重：使用 Map 按 menu.id 去重
5. 排序：按 order 字段升序
6. 返回平铺菜单列表（或构建树形结构）
```

### 2.6 公开接口清单

当前项目中标注了 `@Public()` 的接口：

| 模块 | 路由 | 说明 |
|------|------|------|
| Auth | `POST /api/auth/login` | 用户登录 |
| Auth | `POST /api/auth/register` | 用户注册 |
| Auth | `POST /api/auth/refresh` | 刷新Token |
| Auth | `POST /api/auth/logout` | 用户登出 |
| Menu | `GET /api/system/menu/onlineMenus` | 获取在线菜单 |
| SysConfig | `GET /api/system/config/public` | 获取公开配置 |
| Navigation | `GET /api/navigation/list` | 获取导航列表 |
| Navigation | `GET /api/navigation/detail/:id` | 获取导航详情 |
| NavigationGroup | `GET /api/navigation-group/list` | 获取导航分组列表 |
| NavigationGroup | `GET /api/navigation-group/detail/:id` | 获取导航分组详情 |

## 三、优点分析

### ✅ 1. 默认安全策略（Secure by Default）

通过 `APP_GUARD` 全局注册 `JwtAuthGuard`，所有接口默认需要认证。开发者必须显式使用 `@Public()` 才能开放接口，避免了"忘记加认证"的安全隐患。

### ✅ 2. 三级权限体系设计合理

`认证 → 角色 → 权限` 三级体系层次分明：
- **认证层**（JwtAuthGuard）：解决"你是谁"的问题
- **角色层**（RolesGuard）：解决"你是哪种人"的问题
- **权限层**（PermissionsGuard）：解决"你能做什么"的问题

这种分层允许粗粒度和细粒度权限控制的灵活组合。

### ✅ 3. 双 Token 机制

accessToken + refreshToken 的设计：
- 短期 accessToken 降低 Token 泄露风险
- 长期 refreshToken 避免用户频繁重新登录
- refreshToken 中包含 `type: 'refresh'` 标识，防止 accessToken 被当作 refreshToken 使用

### ✅ 4. 装饰器驱动的声明式权限

权限控制通过装饰器声明，代码可读性强：
```typescript
@Public()                    // 一眼看出是公开接口
@Roles('admin')             // 一眼看出需要管理员角色
@RequirePermissions('user:create')  // 一眼看出需要创建用户权限
```

### ✅ 5. 菜单权限与前端路由联动

`Menu` 模型包含 `path`、`component`、`redirect`、`icon` 等前端路由所需字段，后端直接返回菜单树，前端可据此动态生成路由，实现真正的"后端控制前端菜单"。

### ✅ 6. 软删除设计

Role 和 User 都使用 `isDeleted` + `deletedTime` 软删除，避免误删导致的数据丢失和关联关系断裂。

## 四、缺点分析

### ❌ 1. RolesGuard 和 PermissionsGuard 形同虚设

**严重程度：高**

当前 `@Roles()` 和 `@RequirePermissions()` 在整个项目中**零使用**。守卫虽然代码写好了，但：
- 未通过 `APP_GUARD` 全局注册
- 未在任何控制器方法上标注装饰器

这意味着**所有已认证用户可以访问所有需要认证的接口**，权限控制仅停留在"是否登录"这一层，RBAC 实际上退化为单纯的认证系统。

### ❌ 2. JWT Payload 缺少角色和权限信息

**严重程度：高**

`JwtStrategy.validate()` 只返回 `{ userId, username }`：

```typescript
validate(payload: JwtPayload) {
    return {
        userId: payload.id,
        username: payload.username,
    };
}
```

而 `RolesGuard` 期望从 `request.user.roles` 读取角色，`PermissionsGuard` 期望从 `request.user.permissions` 读取权限。由于 JWT 验证阶段没有查询数据库填充这些字段，即使给接口加上 `@Roles()` 或 `@RequirePermissions()`，守卫也会因为 `user.roles` 和 `user.permissions` 为 `undefined` 而拒绝所有请求。

### ❌ 3. 权限守卫使用 `some` 语义而非 `every`

**严重程度：中**

`RolesGuard` 和 `PermissionsGuard` 都使用 `some`：

```typescript
return requiredRoles.some((role) =>
    user.roles.some((userRole: any) => userRole.code === role),
);
```

这意味着 `@Roles('admin', 'superadmin')` 表示"拥有 admin **或** superadmin 角色即可"，而非"必须同时拥有"。在某些场景下，可能需要"必须同时满足所有角色/权限"的 `every` 语义。当前设计不支持这种需求。

### ❌ 4. Menu.code 与 PermissionsGuard 之间缺少映射

**严重程度：高**

`Menu` 表有 `code` 字段（如 `system:user:list`），`RoleMenu` 关联表记录了角色拥有的菜单。但：
- `PermissionsGuard` 期望 `user.permissions` 是一个字符串数组
- 没有任何代码将用户的 `RoleMenu` 关系解析为 `permissions` 数组并挂载到 `request.user`
- `Menu.code` 和 `@RequirePermissions()` 之间没有建立对应关系

**菜单权限数据存在，但无法被守卫消费**。

### ❌ 5. 登出机制不完整

**严重程度：中**

`AuthService.logout()` 的实现：

```typescript
logout(): { message: string } {
    return { message: '登出成功' };
}
```

这是一个空操作——没有将 Token 加入黑名单，没有在服务端使 Token 失效。只要 accessToken 未过期，已登出的 Token 仍然可以使用。

### ❌ 6. refreshToken 的安全风险

**严重程度：中**

- refreshToken 从请求体传递（`ExtractJwt.fromBodyField('refreshToken')`），而非更安全的方式
- 没有对 refreshToken 做服务端存储和校验——任何持有有效 refreshToken 的人都可以刷新
- 没有 refreshToken 轮换机制——同一个 refreshToken 在有效期内可以无限次使用
- 没有检测 refreshToken 被盗用的机制

### ❌ 7. User.roleType 字段设计冗余

**严重程度：低**

`User` 表有一个 `roleType: String?` 字段（默认值 `"user"`），但同时又通过 `UserRole` 关联表建立了用户-角色的多对多关系。这导致：
- 角色信息存储在两个地方，可能不一致
- `roleType` 的用途不明确，代码中几乎没有使用它做权限判断
- 增加了维护成本

### ❌ 8. 守卫拒绝时缺少友好错误信息

**严重程度：低**

`RolesGuard` 和 `PermissionsGuard` 在拒绝请求时只是返回 `false`，NestJS 会抛出通用的 `403 Forbidden`，但没有说明"缺少哪个角色"或"缺少哪个权限"，不利于前端展示和调试。

### ❌ 9. 部门-角色关联未被充分利用

**严重程度：低**

`RoleDepartment` 表设计了 `autoAssign`（自动分配）和 `defaultPosition`（默认职位）字段，但在代码中没有看到自动分配逻辑的实现。用户加入部门时，不会自动获得部门关联的角色。

## 五、优化建议

### 🔧 建议 1：在 JWT 验证阶段填充角色和权限（优先级：最高）

修改 `JwtStrategy.validate()`，在验证 Token 后查询数据库获取用户的角色和权限列表：

```typescript
// jwt.strategy.ts
async validate(payload: JwtPayload) {
    if (!payload.id) {
        throw new UnauthorizedException('无效的Token');
    }

    const user = await this.prisma.user.findUnique({
        where: { id: payload.id },
        include: {
            roles: {
                include: {
                    role: {
                        include: {
                            menus: {
                                include: { menu: { select: { code: true } } },
                            },
                        },
                    },
                },
            },
        },
    });

    if (!user || user.isDeleted || user.status !== 1) {
        throw new UnauthorizedException('用户不存在或已禁用');
    }

    const roles = user.roles.map((ur) => ur.role.code);
    const permissions = [
        ...new Set(
            user.roles.flatMap((ur) =>
                ur.role.menus.map((rm) => rm.menu.code).filter(Boolean),
            ),
        ),
    ];

    return { userId: user.id, username: user.username, roles, permissions };
}
```

**收益**：使 `RolesGuard` 和 `PermissionsGuard` 真正可用。

**代价**：每次请求多一次数据库查询。可通过缓存优化（见建议 2）。

### 🔧 建议 2：引入权限缓存机制（优先级：高）

为避免每次请求都查询数据库获取权限，可以：

- **方案 A**：将 `roles` 和 `permissions` 直接写入 JWT Payload（Token 体积增大，但零查询）
- **方案 B**：使用 Redis 缓存用户权限，设置与 accessToken 相同的 TTL
- **方案 C**：在 JWT Payload 中存储权限版本号，仅在版本号变更时重新查询

推荐 **方案 B**，兼顾性能和灵活性：

```typescript
// 伪代码
async validate(payload: JwtPayload) {
    const cacheKey = `user:permissions:${payload.id}`;
    let cached = await this.redis.get(cacheKey);
    if (!cached) {
        cached = await this.loadUserPermissions(payload.id);
        await this.redis.set(cacheKey, JSON.stringify(cached), 'EX', 7200);
    }
    return { userId: payload.id, username: payload.username, ...cached };
}
```

### 🔧 建议 3：全局注册 RolesGuard（优先级：高）

在 `auth.module.ts` 中添加 `RolesGuard` 为全局守卫：

```typescript
providers: [
    { provide: APP_GUARD, useClass: JwtAuthGuard },
    { provide: APP_GUARD, useClass: RolesGuard },  // 新增
],
```

然后在需要角色控制的接口上添加 `@Roles()` 装饰器。守卫执行顺序为注册顺序：先认证，再鉴权。

### 🔧 建议 4：建立 Menu.code 权限映射规范（优先级：高）

制定统一的菜单编码命名规范，例如：

```
{模块}:{资源}:{操作}

示例：
system:user:list      — 用户列表
system:user:create    — 创建用户
system:user:update    — 更新用户
system:user:delete    — 删除用户
system:role:assign    — 分配角色
```

然后在控制器中使用：

```typescript
@RequirePermissions('system:user:create')
@Post('create')
async create(@Body() dto: CreateUserDto) { ... }
```

### 🔧 建议 5：实现 Token 黑名单（优先级：中）

使用 Redis 存储已登出但未过期的 Token：

```typescript
async logout(userId: number, token: string) {
    const ttl = this.getTokenRemainingTTL(token);
    if (ttl > 0) {
        await this.redis.set(`token:blacklist:${token}`, '1', 'EX', ttl);
    }
}
```

在 `JwtAuthGuard` 中增加黑名单检查。

### 🔧 建议 6：实现 Refresh Token 轮换（优先级：中）

每次使用 refreshToken 刷新后，旧的 refreshToken 立即失效，返回新的 refreshToken：

```typescript

    // 将旧 refreshToken 加入黑名单
    // 生成新的 accessToken + refreshToken 对
    // 返回新 Token 对

```

### 🔧 建议 7：移除 User.roleType 冗余字段（优先级：低）

`roleType` 字段与 `UserRole` 关联表功能重叠，建议：
- 如果 `roleType` 仅用于前端展示，改为从 `roles` 关联中计算
- 如果 `roleType` 有特殊业务含义，在代码中明确其语义和使用场景

### 🔧 建议 8：增强守卫拒绝的错误信息（优先级：低）

自定义 `ForbiddenException` 携带详细信息：

```typescript

```

## 六、总结

| 维度 | 当前状态 | 目标状态 |
|------|----------|----------|
| 认证 | ✅ JWT 双 Token，全局守卫 | ✅ 已完善 |
| 角色控制 | ⚠️ 代码存在但未启用 | 🔧 需要全局注册 + 填充 user.roles |
| 权限控制 | ⚠️ 代码存在但未启用 | 🔧 需要建立 Menu.code 映射 + 填充 user.permissions |
| Token 安全 | ⚠️ 登出为空操作 | 🔧 需要黑名单 + refreshToken 轮换 |
| 权限缓存 | ❌ 不存在 | 🔧 引入 Redis 缓存 |
| 部门-角色联动 | ⚠️ 数据模型存在但逻辑未实现 | 🔧 实现 autoAssign 逻辑 |

**核心问题**：项目的权限路由体系在**架构设计层面是完整的**（三级守卫 + RBAC 数据模型 + 装饰器），但在**实现层面存在断裂**——JWT 验证阶段不填充角色/权限信息，导致守卫无法工作，整个 RBAC 系统实际上只发挥了"是否登录"这一层作用。最高优先级的优化是在 JWT 验证阶段补充角色和权限数据的加载。
