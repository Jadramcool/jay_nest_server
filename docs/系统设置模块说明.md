# 系统设置模块说明

> 破坏性重构的落地说明：`sys_config` 表 → 代码注册表 + 覆盖值/历史/回滚。
> 迁移脚本：`prisma/migrations/20261016130000_settings_refactor`。

## 1. 设计目标

旧实现的四个结构性问题，决定了这次是重写而不是修补：

| 旧实现 | 问题 | 新实现 |
|--------|------|--------|
| `sys_config` 表存 key/value/type/options/描述 | 声明分散在数据里，删一个设置要删数据；`options` 列根本不存在，`ConfigOptions` 是死代码 | **注册表是唯一事实来源**（`src/modules/settings/registry`），DB 只存"被改过的值" |
| 值以字符串存储，读时靠调用方自己转 | 类型错误运行期才炸 | 强类型读取 `get('site.name')`，按声明类型解析 + 写时校验 |
| 无审计、无并发控制、缓存靠手写失效 | 改错了没法回滚，多实例不一致 | `setting_history` 全量留痕、`expectedVersion` 乐观锁、`setting_revision` 驱动多实例失效 |
| `PASSWORD` 类型明文入库、明文进操作日志 | 泄密面 | 密钥**只走环境变量**（`source: 'env'`，接口只读、不回传、日志只记哈希） |

## 2. 目录与职责

```
src/modules/settings/
├── registry/

│   └── settings-registry.contract.spec.ts   # 契约测试(命名空间/默认值/secret 规则…)
├── settings.service.ts               # 读取/写入/历史/回滚 + 缓存
├── settings-validator.service.ts     # 启动校验(声明错误 / 库中残留 key / env 缺失)
├── settings.controller.ts            # 7 个接口
└── dto/setting.dto.ts

src/modules/maintenance/              # 通用保留期清理(不依赖任何业务模块)
```

## 3. 新增一项设置

> **为什么管理端没有「新增/删除」**：设置项的默认值、类型、分组、可见性都声明在代码注册表，
> 数据库只存覆盖值。若允许在界面新增，就等于往库里写一条"没有声明、没有类型、没有消费方"的记录 ——
> 这正是旧 `sys_config` 的病根：迁移时 12 条里有 **6 条零消费方**（`maintenance_mode`/`page_size`/
> `max_file_size`/`default_language`/`initialized`/`version`），`options` 列根本不存在，
> 唯一能按 key 读任意值的 `resolve` 接口也只被死代码调用。
> 所以：**加设置 = 改注册表 + 接消费方 + 发版**（前端零改动）；
> 管理端只提供 编辑 / 重置(回默认值) / 历史回滚。
> 启动校验会把库里未声明的 key 判为 ERROR（`SETTINGS_STRICT=true` 直接阻止启动）。

```ts
// src/modules/settings/registry/index.ts
...defineGroup({
  'report.retentionDays': {
    type: 'number',        // 决定控件与校验
    default: 180,
    min: 1, max: 3650,
    label: '报告保留天数',
    group: '报表',          // 分组白名单见 SETTING_GROUP_ORDER
    consumer: 'api: report-cleanup.job',   // 必填:消费方,防止"死配置"
  },
}),
```

必须同时**接上消费方**（`SettingsService.get` / 前端 `usePublicSetting`），否则契约测试与启动校验会把它当死配置拦下。
前端设置页无需改动：分组 tab、控件、约束、默认值全部来自 `GET /system/settings/schema`。

### 校验规则（CI 与启动时都会跑）

1. key 必须命名空间化（`site.name`），声明处不允许重复 key；
2. `label` / `group` / `default` / `consumer` 必填，group 在白名单内；
3. 默认值类型必须与 `type` 匹配，`min ≤ max`；
4. `expose: 'secret'` 必须是 `source: 'env'` 且有 `envKey`；
5. `type: 'select'` 必须给 `dictCode`（选项交给数据字典，不重复维护）；
6. 数据库中不允许存在未声明的 key（孤儿覆盖值 → 启动报错，`SETTINGS_STRICT=true` 时阻止启动）。

## 4. 运行时语义

- **读取**：`get(key)` 按类型解析覆盖值，解析/校验失败回退默认值并告警；`getMany` 单次查询避免 N+1。
- **缓存**：进程内 Map；写入精确失效该 key；多实例靠 `setting_revision`（默认 10s 检查一次）整体失效。
- **写入**：事务内 upsert 覆盖值 + 追加历史 + 递增修订号；`expectedVersion` 不一致返回 409。
- **版本号**：同一个 key 上**单调递增**（重置会删掉覆盖值行，所以版本号取自"覆盖值版本与历史最大版本"的较大者 +1）。
  否则重置后再保存会重新从 `v1` 计数，历史里出现重复版本号，回滚按 `(key, version)` 就会命中错误的记录。
- **重置**：删除覆盖值（`source` 回到 `default`），历史 `newValue = null`。
- **回滚**：恢复到该版本**变更前**的值（取该条历史的 `oldValue`，为 `null` 即回到注册表默认值），
  产生新历史（`source=rollback`），不删历史。不重放"变更后的值"——那等于回滚成刚改的值。
- **审计**：设置写接口用 `@OperationLog({ logParams: false })`，操作日志只留"谁改了什么项"，
  **值线索看 `setting_history`**；`secret` 项历史里只存 `sha256:` 哈希。

## 5. 迁移与回滚

迁移做的事（顺序即 SQL 顺序）：建三张新表 → 搬运与注册表默认值**不同**的旧值 →
菜单行原地改写（保留 id 34 / 按钮 id，`role_menu` 关联不断）→ 删除 `sys_config_category` 字典 →
`DROP TABLE sys_config`。

```bash
# 迁移前导出受影响数据(已 gitignore)
npx ts-node -r tsconfig-paths/register scripts/settings-refactor-backup.ts
# 迁移后核对
npx ts-node -r tsconfig-paths/register scripts/settings-refactor-backup.ts --verify
# 需要回退数据时
npx ts-node -r tsconfig-paths/register scripts/settings-refactor-backup.ts --restore storage/backup/settings-refactor-<ts>.json
```

表结构回退：`npx prisma migrate resolve --rolled-back 20261016130000_settings_refactor`，
再部署旧版本代码（旧代码依赖 `sys_config` 表）。

**退役的 6 项**（迁移不搬运）：`initialized`、`version`（不是设置）、
`maintenance_mode`、`page_size`、`max_file_size`、`default_language`（无任何消费方）。
需要恢复时按注册表重新声明并接上消费方。

## 6. 消费方清单

| 设置 | 消费方 |
|------|--------|
| `site.name` | `web-admin`: SideLogo、登录页 |
| `site.description` | `web-admin`: 登录页 |
| `site.copyright` | `web-admin`: 页脚 |
| `site.primaryColor` | `web-admin`: app store 主题色 |
| `security.login.maxRetry` / `lockMinutes` | `api`: `auth/login-guard.service.ts` |
| `notice.retentionDays` | `api`: `maintenance/cleanup.service.ts`（按**发布时间**起算，已发布且未置顶的公告软删除） |
| — 恢复入口 | `web-admin` 公告列表「清理状态 = 已清理」筛选 + 恢复按钮 → `PUT /api/notice/restore/:id`（权限沿用 `notice:delete`） |
| `operationLog.retentionDays` | `api`: `maintenance/cleanup.service.ts`（操作日志物理删除） |
| `system.cleanupEnabled` | `api`: `maintenance/cleanup.scheduler.ts`（应急开关，业务自有的周期任务也建议遵守） |

清理任务：启动 60s 后首跑，之后每 24h 一次；每次运行都重新读设置，所以**改完保留期下一次运行即生效**。
上线前可先干跑评估影响：`CleanupService.runAll({ dryRun: true })` 只统计不落库。

前端读取统一走 `web-admin/src/composables/usePublicSettings.ts`（5 分钟模块级缓存，
管理端保存后调 `invalidatePublicSettings()` 立即生效）。
